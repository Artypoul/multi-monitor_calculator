# /frontend-safety-check

Чек-лист перед открытием **любого** frontend PR. Применять **до** того как пушу ветку. Принципы — из серии нарушений в React-предшественнике (gigma-new); механика здесь — SvelteKit.

## Главная формула

```
Сначала проверяем код и контракт.
Потом делаем UI.
Потом ломаем свой сценарий как ревьюер.
Только потом открываем PR.
```

Не работать «по идее». Если в письме / контракте написано «у нас уже есть X» — **прочитать код и убедиться**. Stop-phrase: «как мы делали раньше», «по такому же паттерну» — открыть оба файла и сверить буква-в-букву.

## Чек-лист (10 пунктов)

Перед `git push` пройти каждый:

1. **Routes / pages / components.** Что уже есть в `src/routes/*` и `src/lib/components/*`. Не плодить дубликаты экранов и виджетов.
2. **Слой данных.** Какие `load` / endpoints в `src/lib/api/*` уже подключены. Не дублировать загрузку, переиспользовать обёртку `client.ts`.
3. **Backend contract — curl'ом.** Для каждого endpoint, который трогаешь:
   ```bash
   curl -s -H "Authorization: Bearer $TOK" \
     -H "Accept: application/json" \
     "https://api-v2.gigma.ru/api/<endpoint>" | python -m json.tool
   ```
   Сверить **все** поля response: какие обязательные, optional, nullable, что значит omitted.
4. **Loading state.** Что юзер видит, пока данные не пришли. Skeleton, спиннер, «Загружаем…». В SvelteKit с `await` в `load` — через `{#await}` или серверный рендер после settle. Не пустой экран.
5. **Empty state.** GET может вернуть пусто (нет данных, `exists: false`). Это **не ошибка**, а нормальный empty с понятной подписью.
6. **Error state.** Network down, 5xx, malformed JSON. `+error.svelte` или inline-error/toast, не silent failure.
7. **401 / 403 / 422.**
   - 401 — единый путь (разлогин / редирект на `/sign-in`) в `client.ts` / `hooks.server.ts`; для публичного endpoint — флаг «не редиректить».
   - 403 — «нет прав» (понятное сообщение, не общий toast).
   - 422 — `errors.<field>` через `fail(422, …)` маппить в красную строку под полем формы, не в общий toast.
8. **Новый пользователь после регистрации.** Что увидит юзер без данных (project / profile / settings). Empty-state, не пустые поля без подписей.
9. **Пользователь с уже заполненными данными.** Returning-юзер: данные подгружены, форма pre-filled, не теряем сохранённое.
10. **Payload не затирает omitted-поля.** Особенно в формах. Не трогал поле X → не отправлять `X: null`. См. «Payload safety».

## Payload safety (особенно для форм)

```
поле не изменилось → НЕ отправляем (или отправляем как было)
поле очищено пользователем → отправляем null или "" ОСОЗНАННО
поле временно не загружено → НЕ отправляем как null
```

### Различия типов

| Значение    | Что означает                                             |
| ----------- | -------------------------------------------------------- |
| `undefined` | поле не трогаем, не отправляем                           |
| `null`      | явная очистка                                            |
| `""`        | пустая строка — **черновик** или **очистка**? Различать! |
| `0`         | валидное число, **нельзя терять** при фильтрации falsy   |
| `false`     | валидное значение, **нельзя превращать в пустоту**       |
| `[]`        | валидный пустой массив                                   |
| `{}`        | валидный пустой объект                                   |

### Антипаттерн (так **нельзя**)

```ts
// Юзер изменил только display_name. Описание не трогал.
await update({
	display_name: form.display_name,
	profile_data: form.profile_data // ← undefined → сериализуется как null → ЗАТРЁТ сохранённое
});
```

### Правильно

```ts
const body: Partial<UpdateRequest> = { display_name: form.display_name };
if (profileDataDirty) {
	body.profile_data = form.profile_data; // только если юзер реально менял
}
await update(body);
```

Альтернатива — на бэке `PATCH` с partial update (не присланные поля = не трогаем).

## Real flow vs test setup

Прямой URL / reload / `location.href` = **полный SSR** (hooks.server + server load с нуля). Реальный пользовательский путь — **client-side навигация** (после `use:enhance` / `goto`), где server load зовётся через fetch, без полного перерендера.

Если smoke прошёл через прямой переход — **не значит**, что реальный flow работает. Проверять либо реально (UI-клики), либо явно подсветить в self-review «test setup отличается от real flow в X». (подробнее — `/flow-debug-checklist`)

## Onboarding & redirect

Любое изменение в onboarding-flow проверять на **всех** сценариях:

- Новый пользователь после регистрации (`needs_onboarding=true`, нет специализаций)
- Пользователь без специализаций (но с `onboarding_completed_at`)
- Пользователь с одной специализацией
- Пользователь с несколькими специализациями
- Пользователь с незаполненным / заполненным профилем

Нельзя проверять только **«мой локальный аккаунт уже работает»** — у нового юзера состояние другое.

## Переиспользование UI

Не делать новый визуальный паттерн, если в `src/lib/components` уже есть похожий. По мере роста проекта держать единый набор примитивов (карточки, формы, layout view-страниц, topbar, sidebar, кнопки) и общие CSS-токены. Профиль (организатор / прокатчик / музыкант) должен выглядеть как часть **единой** Gigma, а не отдельная дизайн-система.

## Specialization-aware UI

Активная специализация **должна влиять** на: меню/sidebar, поля профиля, title/labels, quick actions на дашборде.

**Не хардкодить** by-code в каждом месте. Источник активной специализации — серверная сессия (`active_specialization_id`). Минимальный паттерн:

```ts
// Коды: AGENCY | CONTRACTOR | VENUE | ARTIST | PRIVATE_ORGANIZER
//   (src/lib/types/index.ts; «музыкант» = ARTIST, кода MUSICIAN нет).
// В сессии активная специализация — это active_specialization_id (UUID).
// Каталог { id, code, name } появится в GET /specializations (TODO в specialization.ts).
// Псевдокод (переменной-каталога в коде пока НЕТ):
//   const code = catalog.find(s => s.id === active_specialization_id)?.code;
const profileForm = PROFILE_FORMS[code] ?? PROFILE_FORMS.DEFAULT; // code — из каталога
```

Нейминг (`specialization` vs `participant_type`) и точные коды/endpoints — **свериться с бэком curl'ом**, не на веру. Канон нового фронта — `specialization`.

## Профили специализаций (когда дойдёт до фичи)

1. GET профиля может вернуть «пусто» / `exists: false` — это **не ошибка**, показать форму без pre-fill.
2. PUT/POST отправлять **только осознанные** поля — не трогал `profile_data` → не отправлять (не затирать).
3. `profile_data` может содержать `0` (например, число участников группы) — **не фильтровать** как «empty value».
4. 403 → «Нет прав на редактирование» (понятный текст). 422 → field errors в `errors.<field>`.
5. **Не путать** `projects.name` (название проекта) и `display_name` (имя профиля специализации) — это **разные** поля.

## Frontend safety check блок в self-review

В каждом PR после `gh pr create` добавлять отдельным комментарием:

```markdown
## Frontend safety check

- [ ] Проверил backend endpoint и response shape (curl-логи в self-review)
- [ ] Проверил loading / empty / error states
- [ ] Проверил 401 / 403 / 422
- [ ] Проверил нового пользователя после регистрации
- [ ] Проверил пользователя с существующими данными
- [ ] Проверил, что form payload не затирает omitted-поля
- [ ] Проверил null / undefined / 0 / false / "" / [] / {}
- [ ] Проверил адаптив (1024 / 768 / 480)
- [ ] Переиспользованы существующие компоненты, единый visual pattern
```

Все галки — обязательны для крупного PR. Не проверил — явно написать «не делал, потому что X».

## История уроков (из gigma-new — принципы переносятся)

- **Опция запроса не туда** — параметр положили внутрь объекта запроса вместо корня; заявили «работает как в X» без сверки → не работало. Урок: «по такому же паттерну» = открыть оба файла.
- **PR base = другой ветки** — после merge коммиты ушли не в main. Урок: PR base = master всегда.
- **needs_onboarding из login вместо /user** — поле гарантировано только в `/api/user`. Юзер минул онбординг; smoke через reload маскировал баг. Урок: контракт curl'ом + real flow ≠ reload.
- **Случайный POST в onboarding** — отправили тестовое имя проекта, бэк переименовал реальный проект. Урок: сначала прочитать, что endpoint делает.

Каждая ошибка покрывается одним из пунктов выше. Прошёл бы чек-лист — поймал бы сам.
