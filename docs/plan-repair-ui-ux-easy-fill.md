# План переработки UI/UX: простой ввод для клиента

## Цель

Сделать экран расчета ремонта проще для обычного клиента: человек должен быстро понять, что вводить, получить предварительную стоимость и только потом оставить контакты для точной сметы после замера.

## Текущая проблема

Сейчас flow выглядит как большой мастер на 8 шагов:

- клиент;
- параметры;
- площади;
- работы;
- смета;
- график;
- черновые материалы;
- финишные материалы.

Это полезно для внутренней проверки логики, но тяжело для клиента. Пользователь видит много служебных шагов до главного действия "Рассчитать", а выбор работ выглядит как экспертная настройка, хотя MVP-сценарий уже фиксирован: "Санузел под плитку".

## Новый пользовательский путь

1. Пользователь сразу видит форму "Расскажите об объекте".
2. Выбирает тип ремонта:
   - санузел;
   - вся квартира;
   - комната;
   - кухня.
3. Для санузла вводит только обязательные для расчета поля:
   - общая площадь квартиры;
   - высота потолка;
   - тип санузла;
   - площадь санузла.
4. Видит, что пакет уже выбран: "Санузел под плитку".
5. Нажимает "Рассчитать стоимость".
6. Видит результат:
   - работы;
   - материалы;
   - итог;
   - текст "Точная смета после замера".
7. После результата оставляет заявку:
   - имя;
   - телефон;
   - адрес;
   - удобный способ связи;
   - комментарий.
8. Для остальных вариантов пользователь сразу видит, что быстрый расчет пока не подключен, и может оставить заявку на уточнение сценария.

## Что меняем

- `src/routes/+page.svelte`

  - Убрать восьмишаговый stepper как основной сценарий.
  - Сделать первый экран вокруг выбора типа ремонта, короткой формы объекта и явной кнопки расчета.
  - Не заставлять пользователя вводить имя/телефон до расчета.
  - Не показывать клиенту выбор технических работ до расчета.
  - После результата показать контактную форму рядом с CTA "Оставить заявку".
  - Показать неподключенные варианты ремонта как путь к заявке, а не как отсутствующие возможности.
  - Детали площадей, работ, графика и материалов оставить как вторичные блоки после результата.

- `src/lib/repairFlow.ts`
  - По возможности не менять бизнес-логику и формулы.
  - Использовать существующий пакет `BATHROOM_TILE_DEFAULT_OPTION_IDS`.

## Что не меняем

- Не меняем server-side endpoint `POST /api/repair-estimate/calculate`.
- Не меняем Gigma mapping.
- Не отправляем персональные данные в ERP без отдельного backend-контракта.
- Не добавляем новые backend-сценарии ремонта в рамках этой правки.
- Не переносим внешний редизайн.

## Состояния

- Loading: "Считаем предварительную стоимость".
- Ошибка расчета: "Не удалось рассчитать, попробуйте позже или оставьте заявку".
- Раздельный санузел: оставить human-readable fallback с заявкой на уточнение.
- Невалидные площади: показать ошибку рядом с формой объекта.
- Заявка без имени/телефона: показать ошибку рядом с контактной формой, не перекидывать пользователя назад.

## Responsive

Проверить ширины:

- `<=1024`: форма и summary должны складываться в одну колонку без горизонтального overflow.
- `<=768`: кнопки и поля идут в одну колонку.
- `<=480`: главный CTA остается видимым без обрезки текста.

## Проверки

- `npm run build`.
- `npm run check` с фиксацией известных старых ошибок, если они останутся.
- Browser smoke:
  - открыть `http://127.0.0.1:5173/`;
  - не вводя контакты, заполнить/оставить значения 40 м² / 2.7 м / санузел 4 м²;
  - нажать "Рассчитать стоимость";
  - увидеть works `81320`, materials `12843`, total `94163`;
  - заполнить имя и телефон после результата;
  - нажать "Оставить заявку";
  - увидеть подготовленную заявку.

## Ревью плана

- Product/UX: расчет доступен до контактов, значит friction ниже; заявка остается после результата, когда ценность уже показана.
- Data/security: endpoint и token handling не меняются; персональные данные не уходят в неизвестный backend.
- Frontend safety: технические работы и площади остаются вторичными деталями, а не обязательными шагами клиента.
