# План переноса user flow из Pavel Profi

## Статус

Frontend user flow перенесен в код. Backend, server endpoints, token handling и technical mapping в рамках этого шага не менялись.

## Цель

Перенести из `C:\Users\Art\Downloads\Pavel_Profi_redesign\Pavel_Profi_redesign` не визуальный дизайн и не backend-расчет, а только frontend user flow: параметры квартиры, расчет площадей на экране, выбор наполнения, показ предварительной сметы, графика и списков материалов.

Backend уже готов и используется как headless-сервис. В этой задаче не проектируем и не переписываем его бизнес-логику. Frontend не должен знать technical ids, токены, `composition_id`, `quantity_source` или прямые URL Gigma.

## Граница задачи

Это frontend-задача.

- Frontend переносит шаги, состояния, тексты, локальный расчет площадей и выбор пользовательского наполнения.
- Готовый headless backend принимает пользовательский сценарий и возвращает расчет.
- Если frontend-у не хватает поля в контракте headless backend, это фиксируется отдельным вопросом, а не решается скрытой доработкой backend в рамках этой задачи.
- Server-side Gigma client, token handling и technical mapping не расширяются в этом переносе.

## Источники

- `index.html` — основной пошаговый клиентский сценарий.
- `cmet-shared-engine.js` — старый сметный движок и справочные правила.
- `README.txt` — подтверждает, что в редизайне сохранены формулы, справочники и расчетная логика.

## Целевой user flow

1. Пользователь открывает страницу и сразу видит калькулятор, а не landing-заглушку.
2. На шаге "Параметры" вводит тип квартиры, площадь, высоту потолка и санузел.
3. Нажимает "Рассчитать площади".
4. На шаге "Площади" видит:
   - площадь без санузла;
   - суммарную площадь санузлов;
   - стены всего;
   - полы без санузла;
   - потолки всего;
   - стены санузла под плитку;
   - пол санузла под плитку;
   - периметр плинтуса;
   - разбивку по комнатам и санузлам.
5. Переходит к шагу "Работы".
6. Выбирает категории и позиции работ/материалов. Frontend подставляет количества по умолчанию из рассчитанных площадей.
7. Переходит к шагу "Смета".
8. Frontend отправляет человеческий сценарий в готовый headless-расчет.
9. Пользователь видит предварительную смету:
   - стоимость работ;
   - стоимость материалов;
   - итог;
   - основные работы;
   - материалы;
   - CTA "Оставить заявку";
   - текст "Точная смета после замера".
10. На следующих шагах пользователь смотрит график, черновые и финишные материалы как frontend-представления выбранного сценария.

## Что переносим

1. Шаги сценария:
   - Параметры.
   - Площади.
   - Работы.
   - Смета.
   - График.
   - Черновые материалы.
   - Финишные материалы.
2. Поля первого шага:
   - тип квартиры: студия, 1-комнатная, 2-комнатная, 3-комнатная, 4-комнатная;
   - общая площадь;
   - высота потолка;
   - тип санузла: совмещенный / раздельный;
   - площадь санузла или туалет + ванная для раздельного;
   - сценарий MVP: санузел под плитку.
3. Формулы площадей из оригинала:
   - жилая площадь = общая площадь минус санузлы;
   - комнаты масштабируются от типового шаблона квартиры;
   - площадь стен комнаты = `4 * sqrt(area) * height`;
   - площадь стен санузла считается как квадратное помещение;
   - потолки = общая площадь;
   - периметр плинтуса = сумма `4 * sqrt(room.area)` по комнатам.
4. Справочник категорий работ/материалов:
   - стены, полы, потолки;
   - санузел стены, санузел пол;
   - электромонтаж, сантехмонтаж, освещение, окна-двери.
5. Правила количества:
   - площадные категории получают м² из расчета площадей;
   - штучные категории получают 1 шт по умолчанию;
   - плинтус получает периметр;
   - штукатурка, стяжка и наливной пол получают толщину по умолчанию.
6. Контракт взаимодействия с расчетом:
   - frontend собирает человеческий сценарий;
   - frontend отправляет его в готовый headless-расчет;
   - frontend показывает ответ без технических полей.

## Что не переносим

- Старую верстку и CSS один-в-один.
- Старый большой JS-движок как глобальный script.
- MAX-отправку, Excel-экспорт и UI-автоматизацию.
- Прямой вызов Gigma из браузера.
- Новую backend-бизнес-логику.
- Расширение server-side mapping под все категории оригинала.
- Изменение контракта headless backend без отдельного решения.

## Архитектура

### Frontend

- Хранит состояние шагов и выбор пользователя.
- Считает площади локально, потому что это не секретная логика.
- Показывает категории, выбранные позиции, количества и толщины.
- Отправляет в готовый headless-расчет только человеческий сценарий.
- Обрабатывает ошибки человеческим текстом без технических деталей.

### Headless backend

- Уже существует и остается единственным местом, где живут токены и technical mapping.
- Возвращает frontend-у суммы, работы и материалы по своему текущему контракту.
- Не дорабатывается в рамках этой frontend-фичи.

## Модель данных frontend

Планируемые сущности без привязки к backend internals:

- `RepairFlowInput` — пользовательские параметры квартиры и санузла.
- `AreaCalculation` — рассчитанные площади и разбивки по комнатам.
- `WorkCategory` — категория выбора на шаге "Работы".
- `WorkOption` — одна пользовательская позиция внутри категории.
- `SelectedWorkOption` — выбранная позиция с количеством, единицей и толщиной, если нужна.
- `EstimateView` — данные для показа результата headless-расчета.
- `ScheduleView` — frontend-представление графика по выбранным позициям.
- `MaterialsView` — frontend-представление черновых и финишных материалов.

## Продуктовые решения текущей реализации

1. Показываем все 7 шагов сразу, но недоступные шаги блокируются до расчета площадей.
2. На шаге "Работы" показываем категории оригинала, чтобы сохранить user flow и наполнение.
3. Работы пакета "Санузел под плитку" зафиксированы как часть выбранного пакета, чтобы пользователь не снял их галочкой при расчете этой сметы.
4. Backend-расчет остается только для поддержанного пакета "Санузел под плитку"; остальные выбранные позиции питают frontend-график и списки материалов.
5. Для раздельного санузла frontend считает площади, но не отправляет неоднозначный money-расчет в текущий headless-контракт; вместо этого показывает заявку и текст про точную смету после замера.
6. CTA "Оставить заявку" пока остается заглушкой, как и в предыдущем MVP.

## Ревью плана

- Product: scope сужен до frontend user flow, backend не трогаем.
- Architecture: формулы и справочники выносятся в отдельный frontend-модуль, а не размазываются по Svelte-компоненту.
- Security: расчеты площадей можно делать в браузере, токены и Gigma mapping остаются server-side.
- UX: пользователь видит простой пошаговый путь, без technical wording.
