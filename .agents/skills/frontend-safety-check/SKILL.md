# /frontend-safety-check

Чек-лист перед открытием **любого** frontend PR. Применять **до** того как пушу ветку. Принципы — из прошлых frontend-регрессий; механика здесь — SvelteKit.

## Главная формула

```
Сначала проверяем код и контракт.
Потом делаем UI.
Потом ломаем свой сценарий как ревьюер.
Только потом открываем PR.
```

Не работать «по идее». Если в письме / контракте написано «у нас уже есть X» — **прочитать код и убедиться**. Stop-phrase: «как мы делали раньше», «по такому же паттерну» — открыть оба файла и сверить буква-в-букву.

## Чек-лист (10 пунктов)

Перед `git push` пройти каждый:

1. **Routes / pages / components.** Что уже есть в `src/routes/*` и `src/lib/components/*`. Не плодить дубликаты экранов и виджетов.
2. **Слой данных.** Какие `load` / endpoints в `src/routes/api/*` и `src/lib/server/*` уже подключены. Не дублировать server-side bridge.
3. **Backend contract — curl'ом.** Для каждого endpoint, который трогаешь:
   ```bash
   curl -s -H "Authorization: Bearer $TOK" \
     -H "Accept: application/json" \
     "<local-or-remote-endpoint>" | python -m json.tool
   ```
   Если endpoint публичный и не требует пользовательского токена, не добавлять лишнюю авторизацию.
   Сверить **все** поля response: какие обязательные, optional, nullable, что значит omitted.
4. **Loading state.** Что юзер видит, пока данные не пришли. Skeleton, спиннер, «Загружаем…». В SvelteKit с `await` в `load` — через `{#await}` или серверный рендер после settle. Не пустой экран.
5. **Empty state.** GET может вернуть пусто (нет данных, `exists: false`). Это **не ошибка**, а нормальный empty с понятной подписью.
6. **Error state.** Network down, 5xx, malformed JSON. `+error.svelte` или inline-error/toast, не silent failure.
7. **401 / 403 / 422.**
   - 401 — для публичного calculator endpoint это понятная ошибка bridge/API, не редирект на логин. Если позже появится auth — единый путь обработки в `client.ts` / `hooks.server.ts`.
   - 403 — «нет прав» (понятное сообщение, не общий toast).
   - 422 — `errors.<field>` через `fail(422, …)` маппить в красную строку под полем формы, не в общий toast.
8. **Новый посетитель / первый запуск.** Что увидит юзер без сохранённых данных. Empty-state, не пустые поля без подписей.
9. **Посетитель с уже заполненными данными.** Returning-сценарий: данные подгружены, форма pre-filled, не теряем сохранённое.
10. **Payload не затирает omitted-поля.** Особенно в формах. Не трогал поле X → не отправлять `X: null`. См. «Payload safety».

## Payload safety (особенно для форм)

```
поле не изменилось → НЕ отправляем (или отправляем как было)
поле очищено пользователем → отправляем null или "" ОСОЗНАННО
поле временно не загружено → НЕ отправляем как null
```

### Различия типов

| Значение    | Что означает                                             |
| ----------- | -------------------------------------------------------- |
| `undefined` | поле не трогаем, не отправляем                           |
| `null`      | явная очистка                                            |
| `""`        | пустая строка — **черновик** или **очистка**? Различать! |
| `0`         | валидное число, **нельзя терять** при фильтрации falsy   |
| `false`     | валидное значение, **нельзя превращать в пустоту**       |
| `[]`        | валидный пустой массив                                   |
| `{}`        | валидный пустой объект                                   |

### Антипаттерн (так **нельзя**)

```ts
// Юзер изменил только display_name. Описание не трогал.
await update({
	display_name: form.display_name,
	extra_data: form.extra_data // ← undefined → сериализуется как null → ЗАТРЁТ сохранённое
});
```

### Правильно

```ts
const body: Partial<UpdateRequest> = { display_name: form.display_name };
if (extraDataDirty) {
	body.extra_data = form.extra_data; // только если юзер реально менял
}
await update(body);
```

Альтернатива — на бэке `PATCH` с partial update (не присланные поля = не трогаем).

## Real flow vs test setup

Прямой URL / reload / `location.href` = **полный SSR** (hooks.server + server load с нуля). Реальный пользовательский путь — **client-side навигация** (после `use:enhance` / `goto`), где server load зовётся через fetch, без полного перерендера.

Если smoke прошёл через прямой переход — **не значит**, что реальный flow работает. Проверять либо реально (UI-клики), либо явно подсветить в self-review «test setup отличается от real flow в X». (подробнее — `/flow-debug-checklist`)

## Flow states & redirect

Любое изменение многошагового flow проверять на **всех** сценариях:

- Первый вход без сохранённых данных.
- Повторный вход с уже введёнными значениями.
- Медленный ответ backend / ERP.
- Ошибка backend / ERP.
- Back/forward browser navigation после submit.
- Мобильная ширина `<=480`.

Нельзя проверять только **«мой локальный сценарий уже работает»** — у пользователя в другом состоянии flow может сломаться.

## Переиспользование UI

Не делать новый визуальный паттерн, если в `src/lib/components` уже есть похожий. По мере роста проекта держать единый набор примитивов (карточки, формы, layout view-страниц, topbar, sidebar, кнопки) и общие CSS-токены. Калькулятор и ERP mini-app должны выглядеть как часть **этого** проекта, а не отдельная дизайн-система.

## Repo-aware UI

Для `multi-monitor_calculator` применять этот раздел так:

- Для repair estimate flow: токен Gigma и внешние вызовы остаются server-side, в UI не показывать technical ids и backend-термины.
- Для legacy monitor UI: переиспользовать существующие SMUI/theme-паттерны, а не приносить новый visual language.

## Формы расчёта и заявки

1. GET/config может вернуть «пусто» / disabled option — это **не ошибка**, показать понятный empty/disabled state.
2. POST отправлять **только осознанные** поля — не трогал поле → не отправлять `null` и не затирать сохранённое.
3. Payload может содержать `0` и `false` — **не фильтровать** как «empty value».
4. 403 → «нет доступа к расчёту» или human-readable fallback. 422 → field errors в `errors.<field>`.
5. Не показывать пользователю technical ids, token, endpoint names и backend-термины.

## Frontend safety check блок в self-review

В каждом PR после `gh pr create` добавлять отдельным комментарием:

```markdown
## Frontend safety check

- [ ] Проверил backend endpoint и response shape (curl-логи в self-review)
- [ ] Проверил loading / empty / error states
- [ ] Проверил 401 / 403 / 422
- [ ] Проверил первый вход / пустое состояние
- [ ] Проверил пользователя с уже введёнными данными
- [ ] Проверил, что form payload не затирает omitted-поля
- [ ] Проверил null / undefined / 0 / false / "" / [] / {}
- [ ] Проверил адаптив (1024 / 768 / 480)
- [ ] Переиспользованы существующие компоненты, единый visual pattern
```

Все галки — обязательны для крупного PR. Не проверил — явно написать «не делал, потому что X».

## История уроков

- **Опция запроса не туда** — параметр положили внутрь объекта запроса вместо корня; заявили «работает как в X» без сверки → не работало. Урок: «по такому же паттерну» = открыть оба файла.
- **PR base = другой ветки** — после merge коммиты ушли не в main. Урок: PR base = master всегда.
- **Поле прочитали не из того response** — в одном ответе поле есть, в другом нет; smoke через reload маскировал баг. Урок: контракт curl'ом + real flow ≠ reload.
- **Случайный POST в production-like endpoint** — отправили тестовые данные туда, где backend меняет состояние. Урок: сначала прочитать, что endpoint делает.

Каждая ошибка покрывается одним из пунктов выше. Прошёл бы чек-лист — поймал бы сам.
